# 荣小账压力测试报告（本地测试环境）

> 本报告只针对 `http://127.0.0.1:8000` 本地测试环境，**不是生产环境容量结论**。
> 压测器默认拒绝非 localhost 目标，避免误打生产。

## 1. 测试范围

荣小账没有“下单、支付”业务；实际核心流程是：

- 微信登录/开发登录、会话恢复（`/auth/me`）
- 账本列表（`/ledgers`）
- 首页/统计概览（`/stats/overview`、`/stats/category`）
- 账单列表/详情（`/bills`、`/bills/{id}`）
- 预算状态（`/budgets/status`）
- 记账、AI 转写/确认、共享账本结算、导出（本轮未纳入 5 分钟读压测，建议单独做写场景）

## 2. 测试环境与工具

### 被测环境（本地）

| 项目 | 配置 |
|---|---|
| 机器 | Intel i5-11300H，4 核 8 线程，15.8 GB RAM |
| 可用内存 | 压测开始时约 1.2 GB 空闲 |
| 后端 | `uvicorn app.main:app --reload --host 0.0.0.0 --port 8000`，**单 worker** |
| 数据库 | 本机 MySQL，SQLAlchemy 连接池 `pool_size=20`、`max_overflow=40` |
| 缓存 | 本机 Redis |
| 反向代理 | 无，直连 uvicorn；无 TLS/公网 RTT |
| 数据 | 开发用户 1 个、个人账本 1 个、账单 6 笔 |
| 压测机 | 与被测服务同一台 Windows 主机 |

### 压测工具

- 工具：Python 3.12 + `httpx` 自写异步压测器（Docker daemon 未启动，k6/Locust 未安装）
- 脚本：`loadtest/load_runner.py`
- 特点：只允许 localhost；固定并发 worker；每请求记录延迟、状态码、超时/连接错误
- 未使用 JMeter/Locust/wrk；指标口径与它们一致（平均值、P95/P99、TPS、错误/超时率）

### 与生产环境差异

| 维度 | 本地测试 | 生产需确认 |
|---|---|---|
| 网络 | loopback，无公网 RTT/TLS | 公网 + HTTPS + Nginx |
| 进程 | 单 uvicorn worker + `--reload` | 建议多 worker/多副本，禁止 reload |
| 机器 | 笔记本 4C/8T，内存紧张 | 服务器 CPU/内存未知 |
| 数据库/Redis | 同机共享 CPU/IO | 可能独立实例 |
| 压测机 | 与后端同机，争抢 CPU | 独立压测机更准确 |
| 数据量 | 6 笔账单 | 真实用户数据量/索引压力 |

**结论：本地结果只能用于发现瓶颈趋势，不能直接当作生产并发容量。**

## 3. 场景设计

每轮 5 分钟，固定并发 worker，每个 worker 循环请求；场景权重：

| 场景 | 请求 | 权重 |
|---|---|---:|
| 会话校验 | `GET /auth/me` | 2 |
| 账本列表 | `GET /ledgers` | 3 |
| 账单列表 | `GET /bills?ledger_id=1&page=1&page_size=20` | 4 |
| 账单详情 | `GET /bills/6` | 2 |
| 统计概览 | `GET /stats/overview?ledger_id=1&year=2026&month=7` | 3 |
| 分类统计 | `GET /stats/category?...` | 2 |
| 预算状态 | `GET /budgets/status?...` | 2 |

登录说明：本轮用一次 `/auth/dev-login` 获取 token，再做并发请求。真实微信登录依赖 `wx.login` 的 code，不能直接并发伪造；登录是低频动作，建议单独做 20 次顺序验证。

## 5. 瓶颈定位

1. **单 uvicorn worker（首要）**
   - 50→100 并发时 TPS 仅从 122 到 128，平均延迟从 408ms 翻到 781ms；
   - worker 采样 CPU 约 9.44s/10s（约 94% 单核），说明单事件循环已饱和；
   - 200/500 时 TPS 下降、延迟和连接堆积，500 直接崩溃。

2. **数据库连接池**
   - 每 worker `20 + 40 = 60` 个连接；
   - 200/500 并发下请求排队等连接，出现 15.9s 最大延迟；
   - 500 时本机 8000 端口连接数一度约 1,725，明显超过池容量。

3. **无反向代理/限流/排队**
   - 本地直连 uvicorn；没有 Nginx backlog、连接上限、读接口限流；
   - 单用户可无限打读接口，缺少全局背压。

4. **重复 DB 查询**
   - 每个请求都要 JWT 解出 user 再查 `users`；账本/账单/统计每请求都查库；
   - 统计/预算没有结果缓存。

5. **测试机资源**
   - 压测器与后端同机，开始时仅 1.2GB 空闲内存；
   - 500 档客户端和服务端互相争抢 CPU/端口资源，实际生产多机结果会不同。

## 6. 优化建议（按优先级）

### P0（上线前）
1. 生产禁用 `--reload`，用进程管理器启动多 worker（如 `uvicorn --workers 4` 或 gunicorn），Nginx 负载均衡。
2. 按 worker 数重算数据库连接：`workers × (pool_size + max_overflow)` 必须小于 MySQL `max_connections`，预留 20% 余量。
3. Nginx 设置连接/请求上限、超时和 `proxy_next_upstream`；读接口加用户/IP 级限流。
4. 生产部署前用**独立压测机 + 多用户 token + 真实数据量**复测，不能直接采用本机数字。

### P1
5. 缓存 `/auth/me`、`/ledgers`、统计/预算状态（TTL + 写操作失效）。
6. 为账单列表/统计加复合索引，`EXPLAIN` 验证；用 10 万级账单数据复测。
7. 监控：uvicorn worker CPU/内存、MySQL 连接数/慢查询、Redis 延迟、P95/P99 告警。
8. AI/SSE 单独压测：长连接、外部 LLM 超时、队列长度。

### P2
9. 写入场景单独做 5–10 VU 的创建/编辑/删除测试，观察锁竞争和事务。
10. 共享账本结算/导出单独做并发测试，避免与读流量混在一起。

## 7. 复现命令

```powershell
cd backend
.\.venv_clean\Scripts\python.exe ..\loadtest\load_runner.py `
  --stages 50,100,200,500 --duration 300
```

脚本默认拒绝非 localhost；生产/预发必须显式 `--allow-remote` 并在批准窗口执行。
