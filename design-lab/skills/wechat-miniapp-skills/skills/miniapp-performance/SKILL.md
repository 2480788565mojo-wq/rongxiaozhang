# Mini App Performance

## Principle

先测量，再优化。性能建议必须指向可观察瓶颈，避免为了“性能”牺牲可维护性却没有收益。

## Areas

### Startup & Package

- 检查主包是否包含首屏不需要的页面、组件、图片或依赖。
- 合理分包、独立分包或按需加载（以项目和平台能力为准）。
- 避免把大型 JSON、字典或媒体直接打包进主包。

### Rendering

- 减少无意义节点层级。
- 长列表避免一次渲染海量内容。
- 高频 `setData` 只更新必要字段。
- 不把巨大非视图数据放在渲染 data 中。

### Images & Media

- 根据显示尺寸选择合适资源。
- 合理使用压缩、缩略图、懒加载。
- 避免首屏并发加载大量高清资源。

### Network

- 合并真正可合并的首屏请求。
- 避免页面 onShow 造成无条件重复拉取。
- 缓存稳定数据时定义失效规则。
- 慢接口需要 skeleton/渐进加载，而不是无反馈等待。

### Memory & Lifecycle

- 页面卸载时清理 timer、listener、observer、socket 等资源。
- 大对象不再需要时释放引用。
- 后台切换和重复进入避免重复注册监听。

## Optimization Workflow

```text
现象 → 指标/证据 → 瓶颈 → 最小优化 → 对比验证 → 回归
```

记录优化前后场景和指标，避免“感觉更快”。

## Tradeoffs

缓存会带来一致性成本，预加载会消耗流量，分包会增加首次进入某分包的成本。说明取舍，不把任何技巧绝对化。

## Anti-Patterns

- 没有测量就大规模重构。
- 为减少文件数把所有代码塞在一起。
- 所有接口永久缓存。
- 长列表一次性渲染全部历史数据。
- 页面卸载后仍保留定时器或重复事件监听。
