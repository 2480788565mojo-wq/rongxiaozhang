# Mini App Code Review

## Review Goal

优先发现会造成真实用户影响的问题，不为凑数量做风格挑刺。

## Severity

- `P0`：安全、资金、严重数据破坏或广泛不可用。
- `P1`：核心流程高概率失败、越权、重复关键动作、严重回归。
- `P2`：重要边界、性能、竞态、兼容性或维护风险。
- `P3`：低风险改进。

## Checklist

### Correctness

- 状态分支是否完整。
- 空值/接口缺字段。
- 重复点击。
- 并发与旧响应覆盖。
- 分页和刷新。
- 页面离开后的异步行为。

### Mini Program

- 高频/大对象 `setData`。
- 生命周期和 listener 清理。
- 自定义组件 properties/events。
- 安全区、键盘、长文本和真机兼容。
- 平台 API 权限与失败分支。

### API / Auth / Security

- 是否绕过统一请求层。
- secret/token/敏感日志。
- 客户端越权或信任高价值字段。
- 写接口是否考虑幂等和结果未知。

### UX / Business

- 错误状态是否可恢复。
- 高影响动作是否有必要确认。
- 流程状态是否允许非法动作。
- 是否破坏现有设计系统或交互预期。

## Finding Format

```text
[P1] 标题
位置：path:line
问题：...
影响：...
建议：...
```

没有明确问题时说“未发现阻断项”，并说明未覆盖范围。

## Review Discipline

- 聚焦本次 diff 新增或暴露的问题。
- 只在有证据时报告 finding。
- 风格建议不要伪装成功能 bug。
- 修复建议尽量小、可执行、与现有架构一致。

## Anti-Patterns

- 为显得严格而制造不存在的问题。
- 把个人命名偏好升级成 P1。
- 只看格式，不看权限、竞态、生命周期和写操作。
- 不说明问题实际影响。
- 要求无关的大规模重构作为 PR 前置条件。
