# Mini Program Product Thinking

## Role

把一句模糊需求转成工程团队可以实现、测试和验收的产品定义。不要假设特定行业。

## Requirement Lens

优先回答：

1. 谁在什么场景使用？
2. 用户这一步真正想完成什么？
3. 页面或流程的主行动是什么？
4. 做决定前必须看到哪些信息？
5. 哪些数据来自接口、缓存、系统能力或用户输入？
6. 正常、空、失败、权限不足、重复操作分别怎样表现？
7. 哪些动作不可逆或成本较高？
8. 成功后进入什么状态或页面？
9. 哪些假设必须由产品/后端确认？
10. 如何用明确条件验收？

## Page Definition

复杂页面先形成：

```text
页面目标：
主要用户：
入口：
主行动：
次要行动：

信息结构：
1. ...
2. ...

状态：
- loading
- normal
- empty
- error
- ...

数据来源：
- ...

事件：
- ...

验收标准：
- Given / When / Then ...
```

## Flow Definition

对注册、预约、购买、提交、发布、审批、报名等多步流程，先画出：

```text
触发 → 收集信息 → 校验 → 确认 → 提交 → 处理中 → 成功/失败 → 后续动作
```

明确哪些步骤允许返回修改、哪些需要保存草稿、哪些必须由后端重新校验。

## Interaction Principles

- 一个页面保持明确主任务，主 CTA 不与多个同级按钮抢注意力。
- 删除、支付、提交、取消、发布等高影响动作需要清晰确认与结果反馈。
- 空状态应给下一步，不只是“暂无数据”。
- 错误文案说明发生了什么以及用户能做什么。
- 长流程展示进度，必要时支持草稿或中断恢复。
- 权限请求尽量在用户触发相关功能时发生，而不是无上下文地提前索取。

## Assumptions

需求不完整时允许做最小必要假设，但要区分：

- 可安全默认：视觉间距、普通加载表现。
- 必须确认：计费、权限、审核规则、退款、内容合规、资格判断等业务规则。

不要把推测写成已存在事实。

## Acceptance Quality

验收标准应可观察，例如：

- “请求失败时展示错误态并提供重试按钮”。
- “连续点击提交只产生一次有效业务请求”。
- “未授权定位时仍可手动选择地址”。

避免“体验良好”“逻辑正确”这类无法验证的描述。

## Anti-Patterns

- 把所有需求都塞进一个巨型页面。
- 先写 UI 再想业务状态。
- 只定义正常态。
- 用内部错误码代替用户可理解文案。
- 把行业特有流程误当作所有小程序的默认流程。
