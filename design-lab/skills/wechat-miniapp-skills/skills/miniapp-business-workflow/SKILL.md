# Mini App Business Workflow

## Scope

为所有“用户完成一件业务事情”的流程建模，不绑定具体行业。可用于：购买、预约、报名、申请、提交表单、内容发布、服务下单、优惠领取、审批、退款申请等。

## Model as a State Machine

不要只写一串事件函数。先定义状态和允许动作：

```text
DRAFT
→ VALIDATING
→ READY_TO_SUBMIT
→ SUBMITTING
→ SUCCESS
```

根据业务加入：`REJECTED`、`CANCELLED`、`EXPIRED`、`PARTIAL_SUCCESS`、`PENDING_REVIEW` 等。

实际后端状态优先，不要擅自创造与服务端不一致的枚举。

## Step Design

一个流程通常包含：

1. 输入/选择。
2. 本地基础校验。
3. 服务端预校验或报价（如果需要）。
4. 用户确认高影响字段。
5. 提交写请求。
6. 等待真实业务结果。
7. 成功/失败后的下一步。

## Confirmation Gate

对金额、发布、删除、取消、不可逆提交、敏感权限等高影响动作，在提交前展示真正影响结果的关键字段。避免“确认弹窗”只写一句无信息量的“确定吗？”。

## Idempotency

按钮防抖只能改善体验。重要写操作还需服务端幂等或唯一业务约束。超时后不要直接假设失败；必要时通过查询接口确认真实结果。

## Validation

- 客户端：即时反馈和基础格式。
- 服务端：权限、资格、库存、额度、状态、金额等最终规则。

客户端验证永远不能替代服务端验证。

## Failure Recovery

失败时尽量保留用户已输入信息，并区分：

- 可重试网络错误。
- 业务校验失败，需要修改输入。
- 状态已变化，需要刷新。
- 结果未知，需要查询最终状态。

## Cross-Domain Examples

- 电商：购物车 → 确认 → 创建订单 → 支付。
- 预约：选择服务/时间 → 校验号源 → 确认 → 预约成功。
- 内容：编辑 → 预览 → 发布 → 审核中/已发布。
- 企业流程：填表 → 校验 → 提交 → 审批中 → 完成。
- 活动：选场次 → 填报名信息 → 提交 → 凭证。

这些只是示例，不应固化进通用状态机。

## Anti-Patterns

- 把多步业务流程全部写在一个 `handleSubmit` 中。
- 只用按钮 disabled 当幂等机制。
- 请求超时就立刻再次创建业务记录。
- 客户端自行决定最终金额、资格或审核结果。
- 所有业务都套同一套订单状态。
